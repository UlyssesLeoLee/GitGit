## 1. The central decision: graph storage architecture

This resolves the standing Open Question from Phase 6 §7, carried into master doc §54 and Appendix ADR item 1: **single storage engine vs. graph-store + event-log-with-materialized-view split.**

### 1.1 What each primitive actually needs from storage, at MVP scale

Per Phase 6, the primitive set is Node, Edge, Event, Policy, View (Phase 9's Definition of Done exercises all five). Read literally against what MVP actually does with each:

| Primitive | MVP-era access pattern | Storage need |
|---|---|---|
| **Node** | CRUD by ID; typed property lookup; list-by-type with filters | Anything with indexed rows/documents — no graph-specific engine required |
| **Edge** | Insert on creation (rare, event-driven); traversal 1–3 hops from a known starting Node (Phase 9 DoD step 9: Issue → every downstream Node) | Recursive traversal over a *bounded* hop count, from a *known* root — this is the one access pattern that could plausibly justify a dedicated graph engine, examined in detail below |
| **Event** | Append-only insert; range scan by Node/time; replay for graph-state reconstruction (DTWIN-REQ-001) | A log — append + ordered scan. This is the textbook justification for a relational table with a monotonic sequence column and an index on `(node_id, occurred_at)`, not a stream broker |
| **Policy** | Point lookup + evaluate against a small rule set on the hot path (blocking Policy evaluation per REL-REQ-002) | Low-latency point read; the rules themselves are small, versioned documents |
| **View** | Parameterized query, logged as an Event on invocation (CTX-REQ-002) | A query definition plus its own Event-logged invocation record — no new storage primitive, it's Node+Event again |

**The one real fork in the road is Edge traversal.** Everything else in the table is served adequately by any general-purpose transactional store. So this decision reduces to: *does MVP's Edge-traversal workload need a dedicated graph database, or does PostgreSQL suffice?*

### 1.2 Scrutinizing the graph-database need directly

Phase 9's Definition of Done step 9 is explicit about the actual MVP traversal requirement: **one query, starting from a single known Issue Node, traversing to every Node created across the 10-step loop** (Commit, PR, Review, CI-run, AgentRun — on the order of 5–15 Nodes, 2–4 hops deep, for one Issue). This is not an open-ended "find all paths of unbounded length between arbitrary Node pairs across millions of Nodes" workload — that is the workload dedicated graph databases (Neo4j/Memgraph-class) exist to make fast, and MVP does not have it.

`[FACT]` PostgreSQL supports recursive Common Table Expressions (`WITH RECURSIVE`), which can express bounded-depth graph traversal directly in SQL — this has been a standard PostgreSQL capability since version 8.4 (2009) and is documented core functionality, not an extension.

`[INFERENCE]` For a property graph modeled as an `edges(id, from_node_id, to_node_id, edge_type, properties jsonb, created_at)` table with B-tree indexes on `(from_node_id, edge_type)` and `(to_node_id, edge_type)`, a recursive CTE bounded to depth 4–6 against a graph in the thousands-to-low-millions of Edges (a realistic MVP-to-early-V1 ceiling for a self-hosted single-team-to-mid-org deployment) is a well-understood, adequately-performant pattern — this is a widely-documented technique, not a novel proposal; `[TBD] – Benchmark Required` for the platform's own specific query shapes and node/edge cardinalities, consistent with §44's discipline against inventing performance numbers.

`[INFERENCE]` What a dedicated graph engine (Memgraph, Neo4j) buys over this: (a) genuinely unbounded/variable-depth traversal at speed, (b) native graph algorithms (shortest path, centrality, community detection) as first-class query primitives, (c) better constant-factor performance at very large Edge counts. None of these is exercised anywhere in Phase 9's MVP Definition of Done. (a) and (b) are DTWIN-REQ-003-class ("full simulation/what-if replay") and WKFL-REQ-002-class ("pattern detection over historical Events") capabilities explicitly marked V2/Future by Phase 9 — i.e., the capabilities that would justify a graph engine are precisely the capabilities MVP does not build.

### 1.3 Decision

`[PROPOSAL]` **Single storage engine for MVP: PostgreSQL hosts Node, Edge, Event, Policy, and View-definition data as ordinary relational/JSONB tables. There is no separate graph-store-plus-event-log split at MVP.** Concretely:

- `nodes(id, node_type, properties jsonb, created_at, updated_at)` — one table, `node_type` discriminates the type registry (GRF-REQ-001/006); GIN index on `properties` for property filtering.
- `edges(id, from_node_id, to_node_id, edge_type, properties jsonb, created_at)` — one table (GRF-REQ-002/007); indexed both directions.
- `events(id, seq bigserial, node_id, event_type, actor_id, payload jsonb, occurred_at)` — append-only, never updated or deleted except through GRF-REQ-003's documented erasure exception path; this **is** the audit log (SEC-REQ-003), not a separate subsystem — directly satisfying Principle 6 (graph-native) and the master doc's explicit warning (§38) against re-splitting audit into its own failable subsystem.
- `policies(id, policy_type, rules jsonb, version, active)` — small table, cached in-process.
- Graph traversal (GRF-REQ-008 query API) is implemented as parameterized recursive CTEs over `edges`, depth-bounded by default (CTX-REQ-004-style budget discipline applied to graph queries, not just AI context).

**Why this resolves the tension the Open Question flagged (Phase 6 §7's fear of "recreating GitLab's Gitaly/Praefect/Sidekiq/Workhorse layering at the primitive-storage level"):** a graph-store + event-log split is *itself* the multi-service layering Phase 6 warned about — two storage engines to keep consistent, back up together (BKP-REQ-001), and reason about transactionally. A single PostgreSQL instance gives Node/Edge/Event ACID-consistent writes for free (an agent's Commit Node, its `produced` Edge, and its `AgentRun.completed` Event commit in one transaction), which a split architecture would have to re-engineer as a distributed-consistency problem. This is the 能单体解决 rule applied at the storage layer, not just the service layer.

**Revisit trigger, stated concretely so this isn't re-litigated from scratch later (per Phase 9's own note about the CLOUD-REQ-001 enforcement gap):** re-open this decision if and when *either* (a) production telemetry shows recursive-CTE traversal queries exceeding an agreed latency budget at real Edge counts (a `[TBD] – Benchmark Required` threshold, to be set once §44's benchmarking program runs), or (b) a V2/Future capability requiring unbounded-depth or graph-algorithm queries (DTWIN-REQ-003, WKFL-REQ-002) is actually greenlit for build. Until then, adding Memgraph is optimizing for a workload the platform does not have.

**Migration path if the trigger fires:** PostgreSQL's `edges`/`nodes` tables remain the system of record; a graph engine would be introduced as a **read-only, rebuildable secondary index** fed by the same `events` log (replay-derived, per DTWIN-REQ-001's existing replay guarantee) — never as the primary store, and never requiring a data-model change to Node/Edge/Event themselves, per master doc §16's explicit design goal ("adding a new spec concept later should never require a new structural primitive"). This preserves CLOUD-REQ-003's constraint (no primitive-model changes for scale-out) exactly.

## 3. Git storage decision

Per master doc §17 (GIT-REQ-001–010) and the original spec §22's explicit constraint: 禁止为了"Rust 原生"重复实现已经成熟且高风险的 Git 基础设施 — forbidden to reinvent mature, high-risk Git infrastructure for the sake of "native Rust."

### 3.1 Options considered

| Option | Description | Assessment |
|---|---|---|
| **Custom Git server (reimplement Git protocol/object model from scratch)** | Write pack-protocol, object-store, ref-management logic natively. | Rejected outright by the spec's own explicit prohibition, and independently: this is exactly the highest-risk, lowest-differentiation engineering investment available — GIT-REQ-001's entire point is *indistinguishable-from-standard-Git* compatibility, and Git's protocol/object-model edge cases (partial clone, shallow clone, LFS, submodules, signed commits — GIT-REQ-004/005/007/008) are precisely the kind of long-tail correctness surface a from-scratch reimplementation gets wrong for years. Zero requirement calls for the platform to *be* a novel Git implementation; every Git requirement calls for it to be a **conformant** one. |
| **System `git` CLI as a subprocess** | Shell out to the installed `git` binary for object/pack/protocol operations; wrap it with the platform's own HTTP(S)/SSH transport and hook layer. | `[FACT]` This is precisely how GitHub, GitLab, Gitea, and Forgejo all operate at the core — each maintains its own web/API/permissions layer around the real `git` binary (or, for GitLab, `Gitaly` — see below) rather than reimplementing Git itself. Correctness inherited for free from upstream Git's own decades of hardening; every new Git feature/edge-case fix ships automatically on `git` upgrade. Cost: subprocess-per-operation overhead, and hook/graph-linkage integration (GIT-REQ-006's "graph-aware extensions") has to bridge across a process boundary via Git's own hook mechanism (`pre-receive`/`post-receive`), which is itself a **standard protocol point**, not a private one — directly satisfying the standard-protocol rule. |
| **`libgit2`/`gix` (Rust) bindings — in-process Git object/protocol library** | Link a Git implementation library in-process rather than shelling out. | `[FACT]` `libgit2` is a mature, widely-used C library (used by GitHub itself for parts of its stack, among many others) with permissive licensing; `gix` (`gitoxide`) is an actively-developed pure-Rust Git implementation, meaningfully younger and with a narrower track record of production hardening at GitHub/GitLab's scale — `[UNVERIFIED-FACT]`, flagged for re-verification if `gix` specifically is pursued, since its maturity changes over time and this program should not assume "younger" stays true indefinitely. In-process linking avoids subprocess overhead and gives typed, structured access to Git objects (useful for GIT-REQ-006's graph-aware hooks and Symbol-Node code-intelligence work, §16), but a library re-implementing (gix) or wrapping (libgit2) Git's object model still carries more correctness risk than the actual `git` binary for the highest-risk operations (pack negotiation, protocol v2 edge cases, LFS) — these libraries themselves are known to lag or diverge from canonical `git` behavior on the long tail. |
| **Hybrid** | Use the system `git` binary as the authoritative implementation for all write-path, protocol-level, and pack/negotiation operations (clone/fetch/push/GC); use `libgit2`/`gix` in-process only for read-path, structural queries (walking commit history, reading tree/blob objects for Symbol-Node extraction, diff computation) where correctness risk is lower and latency/ergonomics matter more. | Combines the low-risk-on-the-hard-parts property of shelling out to real `git` with the ergonomics of an in-process library for the read-heavy paths that actually benefit from it. |

### 3.2 Decision

`[PROPOSAL]` **Hybrid: system `git` CLI (subprocess) is authoritative for all write-path and protocol-level Git operations (GIT-REQ-001/002/003/007/008/009); an in-process Git library (`libgit2`, given its longer production track record — re-evaluate `gix` at implementation time against its then-current maturity) is used for read-path structural access (history walks, tree/blob reads, diff computation feeding GRF-REQ's Commit/Symbol Node ingestion) where subprocess overhead would be costly at graph-ingestion volume.** GIT-REQ-006's graph-aware hooks are implemented as standard Git hooks (`pre-receive`/`post-receive`/`update`) that call back into the platform's own API — the hook mechanism itself is Git's own standard extension point, not a private protocol, so this satisfies both the "don't reinvent Git" and "don't invent a private protocol" rules simultaneously. GIT-REQ-010 (Git availability independent of the AI subsystem) is a direct, natural consequence of this design: the `git` binary and its hook path have no dependency on the AI Gateway/Agent Runtime process at all under the single-process-plus-CI-runner boundary in §4 below.

This mirrors what GitHub, GitLab, and Gitea/Forgejo all independently converged on (`[INFERENCE]`, consistent with Phase 3's deep dives cited in master doc §8/§9) — none of them reimplemented Git from scratch either; GitLab's own Gitaly is itself a service wrapper *around* the real `git` binary, not a reimplementation, which is a useful precedent for the wrapper pattern while explicitly avoiding replicating Gitaly/Praefect's own multi-service HA complexity at MVP scale (master doc §9, §13 Principle 2).

## 4. Service/domain boundary map

Governing constraint: 能单体解决，不提前微服务化. Phase 9's MVP loop is one team, one demo-scale deployment, self-hosted or single-region cloud — nothing in its Definition of Done (Phase 9 §6) exercises multi-service scale.

### 4.1 Deployable units for MVP

`[PROPOSAL]`

1. **The Platform process** (single binary/deployment) — hosts: HTTP/API surface (API-REQ-001), Git server wrapper (§3), Node/Edge/Event/Policy/View engine (§1) against PostgreSQL, AI Gateway (AI-REQ-001), Context Engine (CTX-REQ-001/002), Agent Runtime *control plane* (AGT-REQ-001/002/003/004/007 — lifecycle, approval gating, messaging, artifact linkage, graph participation), RBAC/Policy evaluation (SEC-REQ-001, GRF-REQ-004), and the AISEC-REQ controls (§36) that gate what the AI Gateway/Agent Runtime are allowed to do. All in-process function calls, one deployment artifact, one process to start/stop/restart independently of Git-serving per GIT-REQ-010/REL-REQ-001 (achieved by isolating the Git-serving request path so it degrades independently even within one process — a design discipline, not a process-boundary requirement).
2. **PostgreSQL** — the one stateful dependency (§1, §2). A separate process by necessity (any real database is), but not a "service" in the microservice sense — it's the monolith's database, exactly as in a conventional monolithic web application.
3. **Agent execution workspace(s)** — per-AgentRun isolated execution environments (AGT-REQ-005's workspace isolation, SEC-REQ-002's scoped credentials). These are necessarily separate from the Platform process's own runtime for security isolation reasons (an agent must not run inside the same process/privilege boundary that evaluates its own Policy gates), realized as ephemeral containers (or, self-hosted, an equivalent lightweight sandbox) spawned and torn down by the Platform process's Agent Runtime control plane — not standing services, not independently deployed, no independent scaling story at MVP.
4. **CI runner(s)** — similarly, CI execution (CI-REQ-001/004/005) needs its own isolation boundary (R6, §53) distinct from the Platform process for the same reason agent workspaces do. Realized the same way: ephemeral, spawned by the Platform process, torn down after the run, communicating results back via the `events` table plus Postgres `LISTEN`/`NOTIFY` (§2) rather than a message broker.

**Total: one long-running deployable service (the Platform process) plus its database plus ephemeral, on-demand execution sandboxes it spawns.** This is a deliberately conventional monolith-plus-database shape, not a microservice topology — items 3 and 4 are process-isolation boundaries for security (AGT-REQ-005, CI isolation), not independently-scaled "services" in the architectural sense, and they don't have their own APIs, databases, or deployment lifecycles separate from being spawned/reaped by item 1.

### 4.2 Mapped against the primitives and the MVP loop

| Primitive operation | Lives in |
|---|---|
| Node/Edge/Event CRUD, Policy evaluation, View invocation+logging | Platform process, in-process against PostgreSQL |
| Agent as Node subtype — creation, Event emission | Platform process (Agent Runtime control plane), writing to PostgreSQL |
| Agent *execution* (the actual code-writing/tool-calling) | Agent execution workspace (spawned, isolated, ephemeral) |
| CI *execution* | CI runner (spawned, isolated, ephemeral) |
| CI *result* as a graph Node/Event | Platform process, once the CI runner reports back |

| MVP loop step (Phase 9 §1) | Boundary |
|---|---|
| 1. Repository | Platform process (Git wrapper, §3) + PostgreSQL (Repository Node) |
| 2. Issue | Platform process + PostgreSQL |
| 3. AI Context | Platform process (Context Engine + AI Gateway) |
| 4. Agent Branch | Platform process opens the branch via `git` (§3); Agent execution workspace is where the agent itself runs |
| 5. Code Change | Agent execution workspace produces it; Platform process captures/links it (AGT-REQ-004) |
| 6. CI | CI runner executes; Platform process records the graph-visible result |
| 7. AI Review | Platform process (an Agent Runtime invocation scoped to review — no new boundary) |
| 8. Human Approval | Platform process (Policy evaluation + UX-REQ-003's visible control) |
| 9. Merge | Platform process, via `git` (§3) |
| 10. Engineering Graph Update | Platform process + PostgreSQL, throughout — this is the residue of every step above, not a separate step with its own boundary |

**Why this satisfies GIT-REQ-010/REL-REQ-001 without a separate Git service:** the requirement is that Git operations survive AI Gateway/Agent Runtime degradation, not that Git hosting be a physically separate process. Within the single Platform process, the Git-serving code path (§3's `git` subprocess wrapper) has no data or control dependency on the AI Gateway/Agent Runtime code paths — a crashed or hung AI Gateway call does not block a concurrent `git push` request, verified by the isolation discipline (bounded per-request timeouts, no shared locks between the two code paths) rather than by physical process separation. This is cheaper to build and operate at MVP than a genuinely separate Git microservice, and Phase 9's chaos-test Definition of Done (kill the AI Gateway mid-run, confirm Git still works) is testable either way — a separate process is not required to pass that test, only correct isolation within the one process.

## 5. Local → Cloud migration story

Per master doc §13 Principle 3 (Cloud-Ready: same core codebase, no fork) and CLOUD-REQ-001.

**What does NOT change between local and cloud:**
- The Platform process binary/image itself — identical code, identical Node/Edge/Event/Policy/View engine, identical Git wrapper (§3), identical Agent Runtime control plane.
- The data model (PostgreSQL schema for Node/Edge/Event/Policy) — §1's decision to keep everything in one PostgreSQL instance means there is no local-only vs. cloud-only storage topology to reconcile; the schema is the schema everywhere.
- The Agent execution / CI runner spawn-and-isolate pattern (§4.1 items 3/4) — the *mechanism* (ephemeral, isolated, Platform-process-spawned) is unchanged; only *what spawns them* (local Docker vs. a cloud container runtime) differs, which is a deployment-config detail, not an architecture fork.
- Git protocol behavior (§3) — a `git clone` against a local deployment and a cloud deployment behave identically, by construction, since both wrap the same real `git` binary the same way.

**What DOES change:**
- **Deployment wrapper:** `docker compose` (or systemd units) locally; container orchestration (Kubernetes/K3s, per §2's verdict) for cloud multi-node/scale-out. This is packaging, not application logic.
- **PostgreSQL topology:** a single local instance vs. a managed, replicated cloud PostgreSQL (RDS/Cloud SQL/Azure Database-class) with read replicas for scale — same schema, same query patterns, different operational tier. This is exactly the "adopt for MVP" verdict's stated cloud-migration story in §2's table, realized.
- **Horizontal scale-out of the Platform process itself:** locally, one instance; in cloud, multiple stateless Platform-process instances behind a load balancer, all reading/writing the same PostgreSQL — this is possible **only because** the Platform process holds no in-memory state that isn't also in PostgreSQL (Policy rules are cached but PostgreSQL-sourced and safely re-cacheable per-instance) — a direct, load-bearing consequence of §1's single-store decision and the reason CLOUD-REQ-003 ("horizontal scale-out without primitive-model changes") is achievable at all under this architecture, contingent on PostgreSQL itself scaling adequately for the workload (read replicas cover read-heavy graph queries; write scaling is bounded by a single primary, a known PostgreSQL constraint, `[TBD] – Benchmark Required` for whether this ceiling is reached before the storage-architecture revisit trigger in §1 fires for other reasons first).
- **Object/artifact storage backend** (V1+, not MVP): local filesystem locally, S3-compatible object storage in cloud (§2's MinIO/S3 row) — additive, not a rearchitecture, since this capability isn't built at MVP at all.

**Red-flag check (per the task's own instruction):** does this architecture require a *different core design* for cloud? No — the single deviation from "identical everywhere" is deployment packaging and PostgreSQL's operational tier, both of which are standard, expected differences between "one machine" and "a managed cloud fleet" for *any* PostgreSQL-backed application, not something specific or awkward about this platform's design. This is the intended, and achieved, meaning of "local-first, cloud-ready" for this architecture — no fork.

## 7. Revised ADR Required List

Cross-referenced against the master doc's Appendix (ADR Required List, items 1–10) and Phase 9's carried-forward Open Questions. Items now **resolved by this document** are marked so; items still open are retained with updated framing; new ADRs identified by this phase are appended.

1. **Graph storage architecture** — **RESOLVED by this document, §1.** Decision: single PostgreSQL instance hosts Node/Edge/Event/Policy; Edge traversal via depth-bounded recursive CTEs; no graph-store/event-log split at MVP. Revisit trigger stated in §1.3. A formal ADR should still be written recording this decision and its revisit trigger verbatim — this document is the input, not a substitute for the ADR artifact itself.
2. **Policy evaluation distribution model** (centralized vs. locally-evaluable-without-round-trip) — **Still open.** This document's single-process boundary (§4) makes local (self-hosted) Policy evaluation trivially in-process/local by construction — there is no remote round-trip in the local deployment topology at all. What remains genuinely open is the **cloud multi-node** case: whether Policy evaluation stays a local in-process call on each Platform-process instance (each instance re-reading the same PostgreSQL-sourced rules, per §5) or is centralized behind its own endpoint. `[PROPOSAL]` Recommend the former (in-process per-instance, PostgreSQL-sourced) for consistency with §5's stateless-instance scale-out story — but not formally decided here; carried to a dedicated ADR.
3. **Graph state versioning/snapshotting strategy** (for CTX-REQ-002's exact-reconstruction guarantee) — **Substantially informed, not fully resolved.** Because Events are append-only and Node/Edge state is derivable from them (DTWIN-REQ-001, already true under §1's single-store design), CTX-REQ-002's "exact reconstruction" reduces to "replay Events up to a given `seq` value" — a concrete, tractable mechanism given §1's schema (`events.seq bigserial`). `[PROPOSAL]` Recommend the View-invocation log record the `events.seq` watermark at invocation time rather than a wall-clock timestamp, since `seq` gives exact, race-free replay. Still needs a formal ADR to fix retention/compaction policy for old Event ranges.
4. **Horizontal scale-out mechanism for cloud deployment** — **RESOLVED by this document, §5.** Stateless Platform-process instances behind a load balancer, sharing one PostgreSQL (with read replicas), contingent on PostgreSQL write-throughput not becoming the bottleneck first (flagged `[TBD] – Benchmark Required`). CLOUD-REQ-003's priority/timing (previously flagged as contingent on the storage decision, master doc §40) can now proceed on this basis.
5. **Backup/restore point-in-time consistency mechanism** — **RESOLVED by this document, §1.** Because Git objects and the Node/Edge/Event graph are *not* two separate stores requiring distributed-snapshot coordination (Git objects live in the filesystem the `git` binary manages; graph data lives in the one PostgreSQL instance), BKP-REQ-001's consistency requirement reduces to: PostgreSQL's own point-in-time-recovery (WAL-based) plus a filesystem-level Git object snapshot taken within the same maintenance window, coordinated by pausing writes briefly or using PostgreSQL's `pg_backup_start`/`pg_backup_stop` alongside a Git-repository-level snapshot. A formal ADR should still fix the exact coordination mechanism and RTO/RPO targets (BKP-REQ-002, still `[TBD] – Benchmark Required`).
6. **Workspace isolation mechanism for agent/CI execution** — **Still open**, per §4.1's items 3/4 flagging container-vs-VM-vs-sandbox as unresolved implementation detail. `[PROPOSAL]` Recommend starting with container-based isolation (Docker/OCI) for MVP given it's the lowest-operational-weight option consistent with the "no orchestrator needed locally" verdict in §2, with a documented upgrade path to gVisor/Firecracker-class stronger isolation if AISEC-REQ's threat model (§36) is judged to require it at V1 — not decided here, carried to its own ADR.
7. **Secrets store technology and Policy-mediated access design** — **Still open**, not addressed by this phase's storage decision since SEC-REQ-005 explicitly requires secrets to be isolated *from* the graph (i.e., not stored in the same `nodes`/`edges` tables as ordinary graph data) — `[PROPOSAL]` a natural MVP-scale answer is a separate, narrowly-scoped table or a dedicated secrets-management library (e.g., an encrypted-at-rest table with envelope encryption) rather than a new standalone secrets service, consistent with this phase's monolith-first posture — but not formally decided here.
8. **MCP tool-scoping/curation mechanism** — **Still open**, unaffected by this phase's storage/service decisions; genuinely an Agent Runtime implementation-detail ADR, not a storage/deployment-topology question this phase resolves.
9. **GDPR/retention-erasure exception path for the immutable Event log** — **Still open**, pending Legal Review per master doc §54; this document's decision to make `events` an ordinary PostgreSQL table (rather than a specialized append-only log store) makes a documented, audited exception/redaction path for individual rows technically straightforward once the legal requirements are fixed — but the legal determination itself remains outstanding.
10. **CI/CD execution isolation architecture** — **Substantially resolved by this document, §4.1 item 4 / §4.2**, in that CI execution is placed in the same ephemeral-sandbox pattern as agent execution (Platform-process-spawned, isolated, reporting back via `events` + `LISTEN`/`NOTIFY`) rather than a bespoke separate CI subsystem — the specific sandbox technology is the same still-open question as ADR item 6 above, so these two ADRs should likely be written as one.

**New ADRs identified by this phase:**

11. **`[PROPOSAL]` NEW — Implementation language/framework choice (Rust/Tokio/Axum vs. alternatives).** Not resolved by this phase (§2, §6) — flagged as a genuine open engineering decision this requirements-research program is not positioned to make, since no MVP requirement is language-load-bearing. Needs an ADR owned by engineering leadership, informed by team expertise and hiring reality rather than requirements analysis.
12. **`[PROPOSAL]` NEW — `git` CLI vs. `libgit2`/`gix` boundary for the hybrid Git storage design (§3).** This document recommends a hybrid split (subprocess for write/protocol, in-process library for read-path structural access) at the conceptual level but does not fix the exact operation-by-operation boundary — needs a dedicated ADR once implementation begins, including a concrete decision on `libgit2` vs. `gix` specifically (this document flags `gix`'s comparative youth as `[UNVERIFIED-FACT]`, to be re-checked at that time rather than assumed).
13. **`[PROPOSAL]` NEW — CI runner and Agent execution sandbox technology (merges ADR items 6 and 10 above).** Container (Docker/OCI) vs. microVM (Firecracker) vs. other sandbox technology for both agent workspaces (AGT-REQ-005) and CI runs (CI-REQ isolation, R6) — recommend treating these as one ADR since §4 places them in the architecturally identical "Platform-process-spawned ephemeral isolated executor" pattern.
14. **`[PROPOSAL]` NEW — Recursive-CTE query budget/depth-limiting policy for the graph query API (GRF-REQ-008).** §1.2 assumes depth-bounded traversal by default (mirroring CTX-REQ-004's context-budget discipline) but does not fix the actual default depth/row-count limits — needs an ADR once real query shapes are known, ideally informed by the `[TBD] – Benchmark Required` item in §44.
