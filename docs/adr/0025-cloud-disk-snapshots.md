# ADR-0025：云盘（cloud disk）——仓库快照的远端存储与回滚

- 状态：**已接受**（2026-11-18）
- 相关：ADR-0021（凭据 vault 的 S3 形态）、ADR-0022（vault 版本化）、ADR-0023（桌面端合并）
- 影响范围：`src/cloud/`、`src/cli.rs`、`src/main.rs`、`src/error.rs`

---

## 1. 背景

产品要做的事有三件：起一个 Git HTTP 服务器、管一个凭据 vault、给桌面端一个壳。这三件里，**只有仓库数据是「只有本地」的**：

- `[FACT]` **凭据 vault 已经有远端了**：ADR-0021 定了 S3 兼容桶的形态 ✓，`S3Vault` 是 `gitgit key` 的一个后端 ✓；ADR-0022 给了它版本化 ✓，`gitgit key restore` 就是回滚 ✓。
- `[FACT]` **仓库数据没有**：裸仓库在 `<repos_dir>/<name>.git/` ✓，仓里没有它的任何远端副本 ✓，也就没有任何「回到之前那一刻」的办法 ✓。

用户的要求是「支持接云盘，接好之后方便地在云盘存储数据和回滚等操作」。落在这上面，就是：**仓库快照存到远端，并能从任意一份快照把仓库还原回去** ✓。

## 2. 决策

### 2.1 云盘 = S3 兼容的远端

**决策**：云盘的传输是 **S3 兼容** ✓。

**为什么**：

- `[FACT]` 本仓已经两次说 S3 的话 ✓：凭据 vault 用 `rust-s3` 客户端连 S3 兼容桶 ✓（`src/server/vault.rs` ✓），而且**本仓自己就是一个 S3 兼容服务端** ✓（`src/objectstore/` ✓，七个操作 ✓，path-style 寻址 ✓，`x-amz-version-id` 响应头 ✓）。
- `[FACT]` 主流「云盘」里，**阿里云 OSS、腾讯 COS、Cloudflare R2、AWS S3** 都提供 S3 兼容接口 ✓ ⇒ 一个后端覆盖多个云 ✓。
- `[INFERENCE]` OneDrive 与国内消费级网盘走的是 WebDAV ✓，那是 **V1** 的事 ✓：WebDAV 客户端是一套**新协议实现** ✓，而 S3 面只是**换一个 endpoint** ✓。

**代价**：不接 OneDrive/坚果云（V1 再做）✓。

### 2.2 凭据只走环境变量

**决策**：云盘的 access key / secret key **只从环境变量读** ✓，不进命令行 ✓。

- 按盘：`GITGIT_CLOUD_<NAME>_ACCESS_KEY` / `GITGIT_CLOUD_<NAME>_SECRET_KEY` ✓
- 单盘时的兜底：`GITGIT_CLOUD_ACCESS_KEY` / `GITGIT_CLOUD_SECRET_KEY` ✓

**为什么**：与本仓已有的两条规矩同源 ✓ —— AI key 只走 `GITGIT_AI_API_KEY` ✓（`src/ai/mod.rs` ✓），S3 vault 凭据只走 `GITGIT_S3_*` ✓。理由也同源：**命令行参数里的凭据会出现在 `ps` 输出与 shell history 里** ✓。

### 2.3 一份快照 = 一个对象 = 一个 tar 归档

**决策**：一份快照是**一个文件** ✓，格式是：

```text
GITGIT-SNAPSHOT\n
{元数据（一行 JSON）}\n
{一份 ustar 归档}
```

- `[FACT]` 头部是 ASCII 文本 `GITGIT-SNAPSHOT` ✓，所以被人误开的文件一眼能认出来 ✓。
- `[FACT]` 元数据里写着这份快照属于哪个仓库 ✓、什么时候拍的 ✓、归档的 SHA-256 ✓。
- `[FACT]` 归档是 **ustar** ✓（POSIX.1-1988 ✓，系统 `tar` 至今默认写这个格式 ✓），所以用本仓打的快照能被系统 `tar`解开 ✓。

**为什么不是「一个文件一个对象」**：裸仓库有大量 loose object ✓，按文件上传会让一次快照变成上千个对象 ✓，远端无法「一个快照一个文件」✓。

**为什么自己写 tar 而不是加依赖**：本仓不引入新依赖 ✓。ustar 的头部格式是固定的 512 字节块 ✓，写读各百来行 ✓，比引入一个压缩库小得多 ✓。

**明确不做**：压缩（依赖图里没有 flate2 ✓）、超长路径（ustar 自己的 `prefix`+`name` 字段上限 255 字节 ✓，超了是**报错**而不是静默截断 ✓）、符号链接（跳过 ✓ —— 跟随它就可能读到仓库之外 ✓，而裸仓库本来没有 ✓）。

### 2.4 回滚 = 从快照还原

**决策**：`gitgit cloud restore <key>` **替换**当前仓库 ✓——这就是回滚 ✓。

**决策**：还原先解到旁边的暂存目录 ✓，成功后再换上去 ✓ ⇒ 一次失败的还原不会留下半截仓库 ✓。

**决策**：换上去是**三步** ✓ —— 旧仓库让位 ✓、新仓库就位 ✓、旧仓库删除 ✓；第二步失败时旧仓库**回到原处** ✓ ⇒ 一次失败的还原不会把仓库弄丢 ✓。

**决策**：还原前校验归档的 SHA-256 ✓ 与元数据是否相符 ✓ —— 下载被截断或被改过的快照不能变成仓库 ✓。

**决策**：归档里的**每一个路径**在写入任何字节之前先检查 ✓ —— 绝对路径 ✓、`..` ✓、反斜杠 ✓ 一律拒绝 ✓ ⇒ 一个坏快照连一个字节都写不出去 ✓。

### 2.5 快照放哪

**决策**：键是 `<prefix>snapshots/<repo>/<时间戳>-<hash8>.tar` ✓。

**为什么带前缀**：同一桶里可能还有别的东西 ✓；前缀让「这个盘只放 gitgit 的快照」成为一条可检查的规则 ✓。

**为什么带仓库名与时间戳**：键本身就能说明这是什么、什么时候的 ✓ —— `gitgit cloud snapshots` 不用下载任何东西就能列出来 ✓。

**前缀归谁管**：前缀属于**盘** ✓ —— 盘在写出时加上它 ✓、在列举时剥掉它 ✓，盘以上的一切只说**盘内的名字** ✓。这样「写进去的名字」与「列出来、还原时用的名字」永远是同一个 ✓；前缀只在一个地方被拼上 ✓，也就不会出现「按 A 前缀写、按 B 前缀找」这种错 ✓。

## 3. 取舍与未做的事

| 决定 | 取舍 |
| --- | --- |
| S3 面，不做 WebDAV | 覆盖 OSS/COS/R2/S3 ✓；OneDrive/坚果云留给 V1 ✓ |
| 一份快照一个 tar 对象 | 远端可读、可下载、可校验 ✓；代价是每次快照要整体上传一次 ✓ |
| 自写 ustar | 0 新依赖 ✓；代价是只支持普通文件 ✓、路径 ≤255 字节 ✓、单文件 ≤8 GiB（ustar 的 size 字段就这么大 ✓）✓ |
| 还原是替换式的 | 这才是回滚 ✓；代价是现存的未提交改动会丢 ⇒ 所以还原前应当有快照 ✓ |
| 不做增量 / 不做去重 | 一份快照一份完整归档 ✓；代价是重复数据 ✓（V1 再谈） |
| 不备份凭据 vault | vault 已经有自己的远端与版本化 ✓（ADR-0021/0022 ✓） |
| 端到端跑仓内对象存储 | 不需要外网、不需要第三方服务 ✓；代价是第三方端点的行为只能靠同一套协议推 ✓ |

## 4. 验收

1. `gitgit cloud add/list/rm` ✓：盘写进本地注册表 ✓，凭据不进注册表 ✓。
2. `gitgit cloud backup` ✓：仓库打成快照上传 ✓，输出键、大小与摘要 ✓。
3. `gitgit cloud snapshots` ✓：只列键与大小 ✓，不下载 ✓。
4. `gitgit cloud restore` ✓：仓库回到快照那一刻 ✓；损坏的快照被拒 ✓；不是快照的文件被拒 ✓；快照里的路径不能逃出仓库 ✓。
5. 快照文件是 ustar ✓：能被系统 `tar` 读 ✓。
6. 端到端 ✓：对着**仓里自建的对象存储**（`src/objectstore/` ✓）跑一遍真上传 ✓、真列举 ✓、真还原 ✓ —— 这就是本仓自己 ✓，所以这条验收不需要外网 ✓、不需要第三方服务 ✓、也不会被跳过 ✓。

## 5. 未验证

- `[UNVERIFIED-FACT]` 对**第三方** S3 端点（阿里云 OSS ✓、腾讯 COS ✓、Cloudflare R2 ✓、AWS S3 ✓）的一次手工验证还没有做 ✓；本条 PR 里的端到端跑的是仓内自建的对象存储 ✓ —— 它说的是同一套协议 ✓，但第三方实现的行为差异要等真端点才能确认 ✓。
- `[UNVERIFIED-FACT]` 单个大仓库的快照体积与耗时没有实测 ✓（没有压缩 ✓）。
