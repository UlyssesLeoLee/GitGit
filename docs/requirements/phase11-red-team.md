# AI-Native Engineering Platform — Requirements Research: Phase 11

**Status:** v1.0. **Scope:** Phase 11 only (Red Team Review). This document does **not** fix anything — it attacks. Phase 13 (Final Baseline) is where findings get resolved, accepted, or explicitly overridden with reasoning. Builds on and attacks `docs/requirements/00-requirements-definition.md` (master doc), `docs/requirements/phase6-primitives.md`, `docs/requirements/phase9-mvp-reduction.md`, and `docs/requirements/phase10-architecture.md`.

**Posture, verbatim from the originating spec (§45):** adopt the persona of a genuinely adversarial Red Team Reviewer. This is not a validation pass. Every one of the 17 required angles below produces at least one concrete finding with severity, a description, the specific prior-phase artifact it attacks, and either a mitigation or a documented "no action needed" verdict reached through real adversarial effort — not a rubber stamp.

**Tagging convention** (inherited unchanged): `[FACT]` / `[UNVERIFIED-FACT]` / `[INFERENCE]` / `[PROPOSAL]` / `[TBD]`.

## Method

Each of the 17 angles from the original spec is attacked in turn. Findings are numbered RT-01 through RT-19 (some angles yield more than one finding where genuine adversarial effort surfaced multiple distinct problems). Severity is Critical / High / Medium / Low, assigned by potential damage to the program if the finding is real and ignored through Phase 13.

## Angle 1 — Is this just a GitHub clone with AI bolted on?

### RT-01 (Medium)
**Finding:** Strip away GRF-REQ, AGT-REQ, AISEC-REQ, and CTX-REQ from the MVP list (master doc §48) and what remains — GIT-REQ-001/002/003/010, CI-REQ-001, SEC-REQ-001–005, OPS-REQ-001–003, UX-REQ-003, API-REQ-001 — is, feature-for-feature, a minimal self-hosted Git forge with RBAC and CI status. The "AI-native" and "graph-native" claims live entirely in the ~26 remaining MVP requirement IDs, and the master doc's own §48 rebuttal ("roughly half of it... is graph and agent-security infrastructure with no directly visible UI surface on day one") is honest about this but doesn't resolve the risk it names: infrastructure with no visible UI surface is exactly the shape of a differentiator a rushed engineering team quietly deprioritizes under deadline pressure, because nothing in the Definition of Done (phase9-mvp-reduction.md §6) forces a *user* to encounter the graph — only an automated test does. A demo that passes Phase 9's DoD could still *feel* to a real user like "GitHub with an approval button," because UX-REQ-001 (intent-first entry), UX-REQ-002 (context-assembled pages), and UX-REQ-004 (progressive disclosure) — the three requirements that would make the graph *visible and felt* rather than merely queryable — are all V1, not MVP (master doc §48).

**Attacks:** master doc §48 MVP list; UX-REQ-001/002/004 V1 timing.

**Mitigation:** `[PROPOSAL]` Add one UX-facing MVP acceptance criterion beyond UX-REQ-003's approval control: at minimum, the PR/Issue page a human actually looks at during the Phase 9 DoD's manual review checkpoint (step 7) must render at least one graph fact (e.g., the traversal chain from step 9) inline, not just make it queryable via API. Otherwise the differentiator is real in the database and invisible in the product, and "AI-native, not a GitHub clone" becomes a claim provable only to an engineer running a query, not to the developer using the product on day one.

## Angle 2 — Is this AI-washing?

### RT-02 (High)
**Finding:** The vision (master doc §3) and positioning (§4) claim "AI-native" as a structural property, not a feature. But the actual MVP AI surface (Phase 9 §3 Keep List) is: AI-REQ-001 (one provider), CTX-REQ-001/002 (bounded logged retrieval), and AGT-REQ's lifecycle/approval/isolation mechanics. None of AI-REQ-002 (cost observability), AI-REQ-003 (sensitivity routing), AI-REQ-004 (fallback/degradation), or AI-REQ-005 (swap providers without app changes) ship at MVP. That means the MVP's actual AI capability is functionally: call one hardcoded model provider with a bounded context, with none of the multi-provider abstraction that makes "AI Gateway" (Principle 4, §13) a real architectural claim rather than a marketing label for "we call an LLM API." A single-provider, non-swappable AI integration is indistinguishable at the code level from what a well-built "GitHub clone with a Copilot-style bolt-on" would build — the *Gateway* abstraction (the actual differentiator claim) is untested until V1.

**Attacks:** master doc §13 Principle 4 ("AI assistance routes through one internal Gateway abstraction... not a single-vendor bolt-on"); AI-REQ-001/002/003/004/005 MVP/V1 split (Phase 9 §2, §5).

**Mitigation:** `[PROPOSAL]` Either (a) demote the Principle 4 claim's MVP-era wording to "the Gateway abstraction exists in code even if only one provider is configured, verified by an architecture-fitness-function test that a second no-op/mock provider can be swapped in without touching call sites" — mirroring the CLOUD-REQ-001 architectural-discipline un-cut pattern Phase 9 already used for a structurally identical problem — or (b) honestly downgrade "AI-native" positioning language for the MVP-specific claim until AI-REQ-005 ships. Right now the requirements document has the discipline (Phase 9's un-cut precedent) to fix this cheaply but hasn't applied it to AI-REQ the way it applied it to CLOUD-REQ-001.

## Angle 3 — Is this over-engineered?

### RT-03 (Medium)
**Finding:** Phase 6's five-primitive reduction (Node/Edge/Event/Policy/View) and Phase 10's monolith-first architecture are both genuine, well-argued simplifications — this is a case where the program's own anti-over-engineering discipline mostly worked. But one place it arguably didn't: AISEC-REQ carries **eight** distinct requirement IDs (001–008), five of them P0/MVP (Phase 9 §3), each with its own acceptance criteria, for a threat surface (prompt injection, MCP poisoning, tool-description drift, transitive privilege escalation, agent-generated-policy-bypass) that at MVP scale involves exactly one agent framework, one MCP tool allowlist, and one delegation depth (AGT-REQ-009 itself is V1/V2, so AISEC-REQ-005's "transitive chain, at least two hops" acceptance criterion has no MVP-era multi-hop delegation feature to even test against — AGT-REQ-009 is P2/V1+). AISEC-REQ-005's stated MVP acceptance criterion (a three-hop delegation chain test) is testing a scenario (multi-hop subagent delegation) that AGT-REQ-009 — the very requirement that would make multi-hop delegation possible — doesn't exist yet at MVP. That's not over-engineering in the sense of unused product surface; it's a subtler form: a security requirement's acceptance criteria written for a maturity level the rest of the MVP hasn't reached, which risks the team either (a) building a test harness for a delegation depth that can't occur yet, wasted effort, or (b) writing a criterion that trivially passes because there's nothing to attack yet, false confidence.

**Attacks:** AISEC-REQ-005 (master doc §36); AGT-REQ-009 MVP/V1 timing (Phase 9 §5 — confirmed V1/V2, not MVP).

**Mitigation:** `[PROPOSAL]` Phase 13 should either scope AISEC-REQ-005's MVP acceptance criterion down to "single-hop delegation, if any delegation exists at MVP at all" (arguably zero-hop, since AGT-REQ-009 is V1) or explicitly flag AISEC-REQ-005 as "requirement exists and is enforced in Policy logic now, but its test surface is genuinely empty until AGT-REQ-009 ships" — the current wording implies a test that cannot be meaningfully executed at MVP.

## Angle 4 — Is the Engineering Graph actually necessary?

### RT-04 (High)
**Finding:** The entire program's central differentiator claim rests on Phase 5's finding that competitors have "weak linking" (GitHub's three bolted-on systems) rather than no linking at all. GitHub Issues/PRs *are* cross-linked today via `#123` references, closing keywords, and GitHub Projects' relationship fields; GitLab's linked-issues and "Related MRs" features are similarly real, if not queryable as a formal typed graph. The master doc's own competitive matrix (§11, cross-referenced) scores this "❌/⚠️" for competitors — but a red-team reading of that scoring is that it conflates "not a formally typed, queryable graph API" with "no meaningful linking a human or lightweight tool can exploit." Nowhere in Phases 1–10 is there a concrete example of a real engineering task that GitHub's weak linking (issue references + Projects + a search-based reconstruction, roughly what Sourcegraph does per O6) genuinely cannot accomplish, only an architectural argument that it's *less coherent*. Phase 9's DoD step 9 (single-query, multi-hop traversal from Issue to every downstream Node) is the one concrete artifact that would prove the graph is "necessary" rather than "nicer" — but "necessary" is a strong word for a capability whose entire justification is a single benchmarked-but-unmeasured query pattern (`[TBD] – Benchmark Required` per master doc §44) that has never been shown to be something a determined engineer with `gh` CLI, `jq`, and GitHub's GraphQL API cannot reconstruct, slower, but for far less engineering investment.

**Attacks:** master doc §12 Gap Analysis Differentiator tier; §11 Competitive Matrix "Knowledge graph" row; Phase 9 §6 DoD step 9.

**Mitigation:** `[PROPOSAL]` — no full mitigation available at requirements-research level; this is fundamentally a "prove it" gap that only a working MVP can close. Recommend Phase 13 add an explicit acceptance test comparing the graph-native query (Phase 9 DoD step 9) against a scripted GitHub GraphQL API equivalent on a real Issue→PR→CI→Review chain, measuring both correctness *and* latency/effort — if the GitHub-API reconstruction is comparably fast and correct for the reference loop's scale, the "necessary" claim weakens to "more convenient and more consistent," which is a real but much smaller claim than what §3/§4 currently assert.

## Angle 5 — Was Memgraph correctly rejected, or did Phase 10 under-scope future needs?

### RT-05 (Medium)
**Finding:** Phase 10 §1.2's rejection of Memgraph is well-reasoned for the *stated* MVP workload (bounded 2–4 hop traversal from a known root, thousands-to-low-millions of Edges). But Phase 10 §1.2 itself names exactly the capabilities a graph engine would unlock — unbounded/variable-depth traversal, native graph algorithms (shortest path, centrality) — and then dismisses them by pointing at DTWIN-REQ-003 and WKFL-REQ-002 being V2/Future. This is circular: those capabilities are V2/Future *partly because* Phase 9's MVP scoping never asked "what if the graph engine decision constrains what V2/Future can build," and Phase 10 doesn't test that dependency in reverse. Specifically, the Incident Responder persona's job-to-be-done (master doc §6: "trace from the failure straight back to the responsible commit/deployment/agent-run, fast, including cross-repo causes") is exactly a shortest-path/multi-hop-unbounded-depth query across an Incident's `caused_by` chain, potentially spanning many repos and years of history — this is closer to DTWIN-REQ-002's "what changed and why across a time range" than to Phase 9's bounded DoD step 9, and DTWIN-REQ-002 is only P2/V2, meaning the persona whose entire JTBD is "fast graph traversal" (§5 persona table) is explicitly told their core need ships in V2, on an architecture (recursive CTEs) that Phase 10 itself concedes degrades at "very large Edge counts" and doesn't handle "genuinely unbounded/variable-depth traversal at speed."

**Attacks:** phase10-architecture.md §1.2/§1.3 (rejection reasoning); master doc §5 Incident Responder persona; DTWIN-REQ-002 V2 timing.

**Mitigation:** `[PROPOSAL]` The revisit trigger in phase10-architecture.md §1.3 is well-specified for *performance* regression but has no trigger tied to *product* need — i.e., "we greenlit the Incident Responder's cross-repo traceback feature" should itself be an explicit revisit trigger, stated as such, rather than left implicit inside "(b) a V2/Future capability... is actually greenlit for build." Recommend Phase 13 make this trigger a named, first-class line item, not a parenthetical.

## Angle 6 — Is microservices-early avoided, or is MVP secretly fragmented?

### RT-06 (Low)
**Finding, after genuine adversarial effort:** Phase 10 §4 is the strongest section in the whole architecture document on this specific question — one Platform process, one PostgreSQL, and ephemeral spawned-and-reaped sandboxes for agent/CI execution that explicitly "don't have their own APIs, databases, or deployment lifecycles separate from being spawned/reaped." Trying to find a real fragmentation risk: the closest candidate is that "the Platform process" is described as hosting AI Gateway, Context Engine, Agent Runtime control plane, RBAC, and AISEC-REQ enforcement all in-process, which is a lot of distinct concerns for one process boundary to hold correctly (a large in-process monolith can still be a *tangled* monolith even if it's not a microservice mesh) — but Phase 10 doesn't claim modularity-within-the-monolith is solved, only that the deployment topology is a monolith, which is the narrower and correct claim for this phase's scope.

**Attacks:** phase10-architecture.md §4.

**Verdict: No action needed at the architecture-topology level.** The genuine risk here (internal modularity discipline within one large process) is an implementation/code-review concern, not a requirements or architecture-phase finding — flagged as a Medium-priority engineering-process note for Phase 13, not a red-team finding against the requirements themselves.

## Angle 7 — Does Intent Commit add user burden without proportional value?

### RT-07 (Low)
**Finding, after genuine adversarial effort:** ITC-REQ-001/002 (master doc §30) are explicitly Experimental/Future-timed, optional, additive, and ITC-REQ-002 is written specifically to forbid gating a standard `git push` on an intent annotation — the requirement authors already red-teamed this concern themselves and wrote the "developers route around a perfunctory field" risk directly into ITC-REQ-001's own Risks line. There is no MVP or V1 exposure to this risk at all (it's Future-timed), so there's no near-term user-burden risk to attack.

**Verdict: No action needed** — this angle was already substantially defended by the requirement's own text. The one residual concern worth naming for Phase 13, at Low severity: if Intent Commit is ever built, "optional and additive" tends to erode in practice once a Reviewer persona (§5) starts *informally* expecting it on every PR — a social-pressure failure mode no requirement wording prevents. Not actionable at the requirements-writing stage; worth a UX-research note for whichever phase eventually builds it.

## Angle 8 — Is Semantic Diff trustworthy?

### RT-08 (High)
**Finding:** Phase 5's Gap Analysis explicitly places semantic diff in the "Experimental" tier ("research-grade, not proven... interesting, not MVP-worthy"), and DIFF-REQ-002 (master doc §31) correctly writes this constraint into the requirement itself ("MUST NOT be used as the sole basis for a Policy gate... it is a human/agent aid, not a verifier"). That discipline is sound *within §31*. But cross-checking forward: the Incident Responder's JTBD (§6) says "trace from the failure straight back to the responsible commit," and the AI Review loop step (Phase 9 §1, row 7) describes AI Review as "an agent... posts findings as graph-visible output" with **no requirement anywhere restricting what an AI Review agent is allowed to characterize as a "behavioral change."** Nothing stops a review-agent implementation from internally using a semantic-diff-style technique (even an ad hoc LLM-based "does this change behavior" judgment, not the formal DIFF-REQ-001 View) and presenting its conclusion in Review Node output with the same epistemic weight as CI-REQ-002's actually-verified test-pass Evidence Edge. Because Review composition (phase6-primitives.md §4.2) treats "approval Events typically carry Evidence Edges to CI Test Nodes... and possibly to a Policy evaluation record" without a *structural* distinction in the Evidence-Edge convention (GRF-REQ-010) between "verified by executing code" (CI) and "asserted by a model" (AI Review commentary), a Reviewer persona reading a Review page has no graph-structural signal telling them "this Evidence Edge is a fact, that one is an inference" — exactly the failure mode Principle 7 (§13, "Evidence-Native... structurally distinguishable from bare assertions") claims to solve, but GRF-REQ-010's actual specification (master doc, cross-referenced only, no dedicated fields listed) doesn't obviously carry a confidence/epistemic-status tag strong enough to prevent an AI Review's semantic claim from being visually and structurally indistinguishable from a CI Evidence Edge.

**Attacks:** DIFF-REQ-002 (§31); GRF-REQ-010 Evidence-as-specialized-Edge convention (§25); phase6-primitives.md §3.9 Evidence definition ("carries an epistemic status... that a generic Edge doesn't express") — the definition promises this, but no requirement in scope pins down the concrete epistemic-status vocabulary (e.g., `verified` vs. `asserted` vs. `inferred`) as a required, non-optional field.

**Mitigation:** `[PROPOSAL]` Phase 13 should add an explicit acceptance criterion to GRF-REQ-010 requiring every Evidence-typed Edge to carry a mandatory epistemic-status enum (at minimum: `verified` [produced by deterministic execution, e.g. CI], `asserted` [produced by an AI agent's judgment, e.g. AI Review commentary], `attested` [a human's manual claim]) rendered distinctly in any UI surface that shows Evidence (UX-REQ-002). Without this, DIFF-REQ-002's careful "advisory, not authoritative" language for the Experimental semantic-diff feature specifically does not actually stop AI Review — a mainstream MVP feature, not an experimental one — from smuggling in the exact same trust problem under a different requirement ID.

## Angle 9 — Does Emergent UX risk unpredictability?

### RT-09 (Medium)
**Finding:** The phrase "Stable Skeleton + Emergent Context" that the task brief points to does not actually appear verbatim anywhere in the master doc's §33/§34 sections as read — §33 (Emergent Workflow Requirements) and §34 (UX Requirements) never use that phrase or an equivalent formalized principle; the closest analog is UX-REQ-004 ("Progressive disclosure of graph complexity") and UX-REQ-002 ("Context-assembled pages, not fixed page templates"). This is itself a finding: a design principle the original spec apparently intended as load-bearing appears to have been either dropped or renamed somewhere between the original spec and Phase 8's synthesis, with no cross-reference explaining the substitution. Taken at face value, UX-REQ-002's actual wording ("Context-assembled pages, not fixed page templates") is a genuinely risky commitment with **zero teeth**: no acceptance criterion in the cross-referenced Phase 7 UX-REQ set (only summarized, not quoted, at master doc §34) constrains *how much* a page's structure may vary run-to-run for the same Node type, and Phase 12 (Stakeholder Validation, explicitly deferred) is the only place §54's own Open Questions list points to for resolving "UX-REQ-001's... acceptance bar is easy to satisfy shallowly... Phase 12 needs to define this more rigorously." That means the single UX principle most likely to make the product feel inconsistent or unpredictable to a Developer persona ("fast, unsurprising Git/PR workflow," §5) is deferred, unbounded, and — per this red-team pass — not even consistently named across phases.

**Attacks:** UX-REQ-002/004 (master doc §34); master doc §54 Open Questions "UX Validation" (already partially self-aware of this gap, but only for UX-REQ-001, not UX-REQ-002's context-assembly variability risk specifically).

**Mitigation:** `[PROPOSAL]` Phase 13 should require Phase 12 to produce, at minimum, a "stability contract" for UX-REQ-002 before it ships even at V1: a rule such as "the same Node type's page uses the same layout skeleton across all instances; only the *content populated within named regions* varies by context" — i.e., codify a literal Stable-Skeleton/Emergent-Context split as an explicit constraint, not just cite it as an unenforced phrase. Until that exists, UX-REQ-002 is a promise with no falsifiable bound, which is precisely the "repeated without teeth" risk the task brief anticipated.

## Angle 10 — Concrete security risks of agent execution given Phase 10's actual architecture

### RT-10 (Critical)
**Finding:** Phase 10 §4.1 places both Agent execution workspaces and CI runners as ephemeral sandboxes "spawned and torn down by the Platform process's Agent Runtime control plane" — i.e., **the same single Platform process that evaluates Policy (GRF-REQ-004, SEC-REQ-001) also has the privilege to spawn agent/CI sandboxes and issue their credentials (SEC-REQ-002).** AISEC-REQ-006 requires that "an agent MUST NOT be able to self-certify its own output as policy-compliant by virtue of having generated it" — but this requirement is written against the *agent*, not against a compromise of the *Platform process itself*. Phase 10 never asks: if an attacker compromises the one Platform process (e.g., via a dependency vulnerability, or via AISEC-REQ-001's prompt-injection surface escalating beyond its intended blast radius through a bug in the containment mechanism), that single compromise simultaneously controls Policy evaluation, credential issuance, sandbox spawning, *and* the audit Event log that would record the compromise — because SEC-REQ-003's audit trail is (correctly, per §38's own reasoning about avoiding a separately-failable subsystem) the same `events` table the compromised process writes to. This is a real, new attack surface Phase 10's single-PostgreSQL, single-Platform-process decision introduces that AISEC-REQ (written before Phase 10's concrete architecture existed, per Phase 10's own §Next Phases note flagging this) does not cover: **no AISEC-REQ item addresses Platform-process-compromise as a threat model**, only agent/MCP-level threats assuming the Platform process itself is trustworthy. The audit trail's own immutability (GRF-REQ-003) protects against *unauthorized deletion* via the normal API, but a fully compromised Platform process has direct PostgreSQL access and is not meaningfully constrained by an API-level immutability guarantee enforced by that same process.

**Attacks:** phase10-architecture.md §4.1 (single Platform process holds Policy evaluation, credential issuance, sandbox spawning); AISEC-REQ-002/005/006 (master doc §36, none address Platform-process-level compromise); SEC-REQ-003 (structural audit trail — undermined at the root if the writer is compromised); GRF-REQ-003 (immutability enforced at the API/process layer, not at a layer independent of that process).

**Mitigation:** `[PROPOSAL]` This is the single most consequential gap this red-team pass found (see "3 most dangerous findings" below). Recommend Phase 13 add a new requirement domain or extend AISEC-REQ with an explicit "Platform process integrity" requirement: at minimum, (a) PostgreSQL-level write permissions for the `events` table should be structurally more restrictive than the Platform process's general read/write role (e.g., an append-only grant, no UPDATE/DELETE at the database-role level, independent of what the application code enforces), so a compromised Platform process cannot silently rewrite its own audit trail even with full application-layer compromise; (b) credential-issuance and Policy-evaluation code paths should be reviewed for privilege separation *within* the monolith (least-authority modules, not just least-privilege agents) even though Phase 10 correctly rejects splitting these into separate microservices for MVP; (c) explicitly document this residual risk in the Risk Register (master doc §53) as a distinct risk from R3/R7/R8, since none of the existing ten risks name "compromise of the Platform process itself" as a scenario.

## Angle 11 — Is local deployment too heavy?

### RT-11 (Medium)
**Finding:** Phase 10 §6's "Components Rejected/Deferred" table is genuinely disciplined about *individual* component weight (Memgraph, K3s, NATS, Valkey all correctly deferred), and each row's reasoning is sound in isolation. But no section anywhere in Phase 10 sums the **cumulative** footprint of what MVP *does* run locally: (1) the Platform process itself (language/runtime TBD, §7 ADR item 11 — Phase 10 explicitly declines to estimate this), (2) PostgreSQL (~100–300MB idle, `[INFERENCE]`, §2), (3) at least one ephemeral agent execution sandbox per active AgentRun (container-based per the §7 ADR item 6 recommendation — Docker/OCI has its own base daemon overhead beyond the sandboxed workload itself, not counted anywhere), and (4) at least one ephemeral CI runner sandbox per active CI run, potentially concurrent with (3) during the loop's steps 5–6. OPS-REQ-005 requires "resource footprint documented and bounded for small deployments" as a P1 requirement — but it is **V1-timed, not MVP** (Phase 9 §5), meaning the MVP is permitted to ship self-hosted with *zero documented resource footprint claim at all*, while §13 Principle 2 ("Local-First... a design constraint checked from day one") and the "local-first, lightweight" framing implicit throughout Phases 1–10 is a claim nothing in MVP scope actually tests or bounds. A laptop running Docker Desktop, a Postgres instance, and two concurrent ephemeral containers (one agent sandbox, one CI sandbox) during the loop's steps 4–6 is a materially heavier local footprint than "clone GitHub Enterprise Server-lite," and this program has no MVP-era check that it stays within a "small team laptop" envelope.

**Attacks:** OPS-REQ-005 MVP/V1 timing (Phase 9 §5 — confirmed V1, not MVP); phase10-architecture.md §2 (Docker/OCI adopted for both agent and CI isolation, cumulative overhead never summed); §13 Principle 2 (Local-First claim).

**Mitigation:** `[PROPOSAL]` Pull OPS-REQ-005 forward to MVP, or at minimum require the Phase 9 DoD's chaos test (step 10) to also record peak concurrent RAM/CPU during a full loop run as an informational (non-gating) metric — cheap to add to an already-required integration test, and it converts "local-first, lightweight" from an assumed brand claim into an actually-measured one before the platform's first real users self-host it on hardware smaller than the team's own dev machines.

## Angle 12 — Is the MVP still too big? (Second independent pass)

### RT-12 (High)
**Finding — re-deriving independently, not citing Phase 9's own conclusion:** Picking five specific MVP requirements and re-testing each against the loop, adversarially:

1. **AGT-REQ-006 (resource limits on agent execution), P0/MVP.** Genuinely load-bearing per Phase 9's own reasoning ("an MVP demo can trivially run away on cost/time" without it) — re-derivation agrees. **Defend: correctly kept.**
2. **SEC-REQ-004 (least-privilege default for new agents/integrations), P0/MVP.** Re-testing: does the 10-step loop actually exercise "new agent/integration onboarding" as a distinct scenario, or does it only exercise one pre-existing, already-configured agent acting within an already-granted scope? Reading Phase 9 §6 DoD step 3 closely: it tests that "the agent cannot read/write any repository or credential outside its granted scope" — that is SEC-REQ-002/AGT-REQ-005's job, not SEC-REQ-004's ("least-privilege **default** for **new** agents"). Nothing in the DoD actually onboards a *new* agent and checks its default grant is minimal; the DoD's agent is presumably pre-provisioned for the test. **This is a genuine gap**: SEC-REQ-004 is MVP-timed but not exercised by the MVP's own acceptance test, an inconsistency of the same shape Phase 9 itself caught and fixed for GRF-REQ-009/010 (§5 footnote) but didn't catch here.
3. **CTX-REQ-002 (context assembly is a logged View invocation), P0/MVP.** Re-testing: is the *logging* of context assembly load-bearing for the loop to run, or only load-bearing for the loop to be *auditable* afterward — a distinction Phase 9's own load-bearing test (§1: "the loop breaks or degenerates... without it") should apply strictly to. The loop's steps 1–9 would still functionally complete (an agent still gets context, still branches, still merges) if CTX-REQ-002's Event-logging half were absent — only step 10 (Engineering Graph Update / the audit-trail claim) breaks. Phase 9's own text concedes this directly ("CTX-REQ-002 specifically is what makes step 10's graph residue meaningful for the context step, not just the code-change step") — meaning CTX-REQ-002 is defended as load-bearing *for step 10's differentiator claim*, not for the loop's mechanical completion, which is a slightly different (and legitimate, but more honestly stated as "load-bearing for the *point* of the loop, not the loop's *execution*") justification than the "loop breaks without it" framing implies elsewhere. **Defend, but flag the justification's rigor as inconsistent with the stated test.**
4. **API-REQ-001 (single documented API surface), P0/MVP, narrowed per Phase 9.** Re-testing: the loop's steps 1, 3, 8 need *some* interface, but does that interface need to be **single and documented** — the actual requirement text — or would three separate ad hoc internal interfaces (Git wrapper, Context Engine call, approval endpoint) that happen to all live in the same process also make the loop run? A "single, documented" API is a hardening/consistency claim on top of "an interface exists," similar in shape to the AI-REQ-002/003 cuts Phase 9 already made. **Genuine candidate for further narrowing**: keep "an interface exists and is Policy-gated" as load-bearing (this is real, ties to AISEC-REQ-006's anti-bypass concern), but "documented" specifically (developer-facing docs, versioning discipline) is arguably V1 hardening exactly like API-REQ-003 was correctly demoted.
5. **UX-REQ-003 (Human Authority visible/actionable), P1-but-treated-as-MVP.** Re-testing: this is the one item Phase 9 explicitly flagged as a Priority/timing exception ("P1, but treated as MVP given how directly it operationalizes the Human Authority principle"). Re-deriving from the loop test alone (ignoring the principle-alignment argument): step 7 requires "a visibly distinct, in-context, actionable control" — a genuinely minimal UI (a single unstyled approve/reject button with no context-page investment) satisfies the DoD's literal acceptance criterion. **Defend as correctly MVP-timed**, but flag that its bar is currently satisfiable by something far cruder than what "Human Authority is a core principle" rhetorically implies (§13 Principle 8) — this is a scope-creep risk in the *opposite* direction: a team could satisfy UX-REQ-003 literally while betraying its spirit, with no requirement currently distinguishing "technically visible" from "actually legible to a human under real review load."

**Attacks:** SEC-REQ-004 (§35), CTX-REQ-002 (§26), API-REQ-001 (§47), UX-REQ-003 (§34), all cross-checked against Phase 9 §1/§6.

**Mitigation:** `[PROPOSAL]` Phase 13 should (a) add an explicit "new agent onboarding with default-minimal scope" step to the DoD or accept SEC-REQ-004 as MVP-timed-but-untested (documented honestly, not silently); (b) no change needed for CTX-REQ-002 beyond noting the justification-consistency issue for future phases' benefit; (c) consider narrowing API-REQ-001's MVP acceptance criterion to drop the "documented" half to V1, mirroring API-REQ-003's precedent, if engineering capacity is tight; (d) add a minimal legibility bar to UX-REQ-003 (e.g., "the approval control must show, at minimum, the specific Action being approved and the actor requesting it, not merely an undifferentiated approve/reject button") so the requirement can't be satisfied in letter while failing in spirit.

## Angle 13 — Did Phase 10 underestimate Git infrastructure complexity?

### RT-13 (High)
**Finding:** Phase 10 §3's hybrid `git`-CLI-plus-`libgit2` decision is well-reasoned against the specific risk it names (don't reimplement Git), but stress-testing it against the concrete edge cases the task brief calls out:

- **Concurrent pushes / ref-update races:** Phase 10 §3 says nothing about how concurrent pushes to the same branch/ref are serialized when the platform's `pre-receive`/`post-receive` hooks (used for GIT-REQ-006's graph-aware extensions) call back into the Platform process's API mid-push. If that callback is synchronous and blocking (needed to let Policy evaluation gate a push per GRF-REQ-004/REL-REQ-002), two near-simultaneous pushes to different branches of the same repo could serialize on Git's own ref-lock behavior *plus* an additional Platform-API round-trip per push, and nothing in Phase 10 estimates whether this compounds badly under real concurrent-team load (the exact scenario OPS-REQ-003's "LAN-scoped multi-user operation" is supposed to support).
- **Large monorepos:** GIT-REQ-007 (partial/shallow/sparse clone) is correctly flagged P1/V1, not MVP — but Phase 10's read-path `libgit2` usage for "graph-ingestion volume" (§3.2) history walks and tree/blob reads for Symbol-Node extraction is never load-tested against monorepo scale, and no requirement bounds *how much* of a repository's history the Platform process eagerly ingests into Commit/Symbol Nodes on push — an unbounded ingestion policy against a genuinely large monorepo could make GRF-REQ's write path the actual scaling bottleneck long before PostgreSQL's read-query performance (the thing §44/§1.2 actually flags for benchmarking) becomes the issue.
- **LFS:** Correctly deferred to V1 (GIT-REQ-004) — no MVP claim to attack here, defensible.
- **Repository locking / GC:** Neither Phase 10 nor any GIT-REQ item mentions Git's own garbage-collection (`git gc`) or repack behavior at all — a real self-hosted forge running for months accumulates loose objects and eventually needs GC, which briefly locks repository access; this is invisible in every phase of this program.

**Attacks:** phase10-architecture.md §3 (hybrid decision, no concurrency/locking analysis); GIT-REQ-006 (graph-aware hooks, no synchronous-callback-latency analysis); GRF-REQ ingestion path (no bound on history-walk volume per push).

**Mitigation:** `[PROPOSAL]` Phase 13 should add: (a) an explicit requirement or ADR item for push-time hook callback latency budget and behavior under concurrent pushes to the same repo (fail-open vs. fail-closed under contention, tying to REL-REQ-002's existing "fail closed on Policy-evaluation timeout" precedent — but that precedent isn't currently connected to the Git-hook path specifically); (b) a bound on per-push graph ingestion volume (e.g., only newly-reachable commits since the last known ref position, not a full history walk) stated as an explicit acceptance criterion on GIT-REQ-006 or GRF-REQ-006; (c) a new, currently entirely absent requirement for repository maintenance (GC/repack) scheduling and its interaction with concurrent read/write access — flagged as a gap with zero prior-phase coverage, not merely under-specified.

## Angle 14 — Is AI cost/inference cost viable at the proposed usage pattern?

### RT-14 (Critical)
**Finding:** AI-REQ-002 (cost and token observability per request) is demoted from MVP to V1 by Phase 9 (§2), on the reasoning that "the loop functions without it." That's true in the narrow load-bearing-test sense Phase 9 applies consistently elsewhere — but cross-checking the actual usage pattern the MVP loop implies: **every single loop run invokes at minimum two AI calls (AI Context assembly's model use if CTX-REQ-001 is embedding/LLM-based, plus the AI Review step) and at least one full agentic coding session (the Agent Branch → Code Change steps, which for any real coding agent means many tool-call round-trips, not one API call).** A self-hosted MVP adopter (the exact persona OPS-REQ-001/002/003 targets — a small team running this on their own hardware, paying their own AI provider bills directly since AI-REQ-001 is "one working provider," typically a paid frontier-model API) has **zero cost visibility into what each loop run costs them** until V1 ships. This is a genuine near-term financial risk, not a hypothetical one: an early adopter running this MVP loop repeatedly (the whole point of adopting it) against a metered API has no requirement-guaranteed way to know their spend is accumulating dangerously until a bill arrives — worse than most AI coding tools available today, nearly all of which surface at least basic token/cost counters in their existing UIs (Claude Code, Cursor, Codex CLI all do this per Phase 1-5's own competitive research, though not cited by ID in this document to avoid re-deriving Phase 3's specific citations). Demoting AI-REQ-002 out of MVP means this platform's MVP is *less transparent about AI cost than the very competitors it positions against* (§4), on a feature dimension (cost) that is directly load-bearing for whether a self-hosted small team can safely run the reference loop repeatedly without financial surprise — arguably as load-bearing as AGT-REQ-006's resource limits, which Phase 9 *did* correctly keep at MVP for exactly this class of risk ("an MVP demo can trivially run away on cost/time").

**Attacks:** Phase 9 §2 (AI-REQ-002 demotion); AGT-REQ-006's MVP-keep reasoning (identical risk class, opposite MVP-timing decision — an internal inconsistency); master doc §4 positioning claim (implicitly promises parity-or-better vs. competitors that already have basic cost visibility).

**Mitigation:** `[PROPOSAL]` This is one of the three most dangerous findings (see rollup below). Recommend Phase 13 either (a) pull a minimal slice of AI-REQ-002 into MVP — not full per-request cost/token observability with dashboards, just a running total surfaced somewhere the operator can see it, mirroring how AGT-REQ-006's resource limits were kept minimal-but-present — or (b) if AI-REQ-002 genuinely stays V1, add an explicit, prominent MVP-era warning/disclaimer requirement (a new small requirement, or an addendum to OPS-REQ-002) that MVP operators are told, unambiguously, at setup time, that AI spend is currently unmetered by the platform and they must rely on their provider's own dashboards — the current documents are silent on this, which risks a genuinely bad first experience for exactly the self-hosted-adopter persona the whole "local-first" positioning is built to attract.

## Angle 15 — Should mature open-source components have been reused instead of building custom?

### RT-15 (High)
**Finding, scanning across all phases:** Phase 10's component evaluation table (§2, §6) is genuinely thorough for *infrastructure* components (Postgres, Memgraph, NATS, etc.) — reuse-vs-build was actually done well there. But the same discipline was not applied to the **application-layer** build decisions, where "build custom" is implicitly assumed without ever naming an OSS alternative to reject:

- **The Git forge/web layer itself.** Nowhere in Phases 1–10 does the program evaluate forking or embedding **Gitea or Forgejo** — both surveyed in depth in Phase 1–5 (master doc §7 lists them as deep-dived) as MIT-licensed (Gitea) / MIT-licensed-with-non-profit-governance (Forgejo) Git forges that already implement GIT-REQ-001–009's entire surface (protocol compliance, branch/tag ops, LFS, submodules, hooks, partial clone, signed commits, mirror import) to production quality today. Phase 10 §3 evaluates "custom Git server," "system git CLI," "libgit2/gix," and "hybrid" — but never asks "extend Forgejo/Gitea's existing, working implementation of exactly this requirement set, and add the graph/agent layer on top of or beside it" as a fifth option. Given Forgejo's non-profit governance is *independently praised* elsewhere in this same program (master doc R11: "Forgejo's non-profit governance explicitly removes 'rug-pull risk'") as a positive signal, the failure to seriously evaluate building *on* it rather than *reproducing its entire feature surface from scratch* is a genuine gap, not a minor one — GIT-REQ's 10 requirements represent real engineering effort (correctness-critical Git protocol handling, per Phase 10 §3's own "highest-risk, lowest-differentiation" framing) that an existing, MIT-licensed, actively maintained project has already spent years getting right.
- **The graph query/traversal layer, if usage ever exceeds Postgres CTEs.** Phase 10 rejects Memgraph specifically, but never evaluates **Apache AGE** (a mature, actively-developed, Apache-2.0-licensed PostgreSQL extension providing openCypher graph queries *inside* PostgreSQL itself) as a middle option between "recursive CTEs" and "a separate graph database service" — this would have let Phase 10 get closer to genuine graph-algorithm capability (Angle 5's concern) without violating its own "don't add another database early" rule, since AGE runs inside the same PostgreSQL instance already adopted. `[UNVERIFIED-FACT]` — AGE's specific production maturity and license terms should be independently re-verified before treating this as a firm recommendation, consistent with this program's own evidence discipline, but its complete absence from Phase 10's evaluation table is itself the finding.
- **The MCP tool-scoping/curation mechanism** (ADR item 8, phase10-architecture.md §7 — still open) has no evaluation against existing MCP gateway/proxy projects in the growing MCP ecosystem that already implement allowlisting and tool curation, several of which existed and were documented by the time of Phase 10's writing.

**Attacks:** phase10-architecture.md §3 (Git storage decision, no Forgejo/Gitea-embedding option evaluated); §1/§6 (Memgraph rejection, no Apache AGE middle-option evaluated); §7 ADR item 8 (MCP scoping, no existing-gateway evaluation).

**Mitigation:** `[PROPOSAL]` Phase 13 should require a dedicated build-vs-embed evaluation for the Git forge layer specifically before implementation begins — even if the eventual conclusion remains "build against the real `git` binary directly, because Gitea/Forgejo's own data model and web layer would need to be substantially rearchitected to host the Node/Edge/Event graph as a first-class citizen rather than a bolt-on, which is exactly the anti-pattern this program exists to avoid" — that conclusion, if reached, should be an explicit, argued ADR decision, not an unexamined default. Similarly, Apache AGE should be added to the graph-storage revisit-trigger discussion (Angle 5's mitigation) as a candidate "middle option" evaluated at that time, not skipped straight to Memgraph-class dedicated graph databases.

## Angle 16 — Why would a user choose this over GitHub/GitLab?

### RT-16 (High)
**Finding:** Phase 5's claimed differentiators (master doc §12, restated §3/§4) are: (a) the knowledge graph, (b) true self-hosted+cloud parity with agent-native execution, (c) unified audit trail. Testing switching cost against these: a team currently on GitHub or GitLab already has years of accumulated Issues/PRs/CI history, existing integrations (Slack, Jira, deploy pipelines), and trained muscle memory. GIT-REQ-009 (mirror/migration import) covers *Git object* migration, but **nothing in this program's 100+ requirements addresses migrating existing GitHub Issues, PR history, or CI configuration into the new platform's graph** — DATA-REQ covers *exporting from* this platform (anti-lock-in, outbound), but there is no symmetric *importing history into* this platform's graph from an incumbent forge. That means the switching cost is not just "learn a new tool" but "either start your engineering graph from zero (losing years of Issue/PR/incident history that a real Architect or Incident Responder persona's JTBD explicitly depends on — §6: "trace... including cross-repo causes" implies historical depth) or accept the new platform only for new work while old history stays trapped in GitHub." Differentiator (a), the graph, is *least* valuable on day one for a switching team precisely because the graph starts empty — its value compounds over time, which is the opposite of what a switching decision needs to see to justify the migration cost.

**Attacks:** master doc §4 positioning; GIT-REQ-009 (Git-object-only migration scope); DATA-REQ (export-only, no import-of-non-Git-history requirement anywhere in scope).

**Mitigation:** `[PROPOSAL]` Phase 13 should either explicitly scope a GitHub/GitLab Issue+PR+CI-history import capability (symmetric to DATA-REQ's export story) into V1/V2, or explicitly acknowledge in the Non-Goals/Risk Register that "cold-start graph" is an accepted adoption-cost tradeoff and the platform's early go-to-market should target **new** projects/teams rather than migrations, which is a materially different (and currently unstated) positioning decision with real implications for §4's "for engineering organizations that need to run AI coding agents at scale" framing, which reads as targeting existing, presumably GitHub/GitLab-resident organizations.

## Angle 17 — Which 3 features would be a genuine 10x UX improvement, and does MVP contain them?

### RT-17 (Critical)
**Finding:** Candidate 10x features, derived from the program's own stated differentiators and persona JTBDs (§5/§6): (1) **one-query cross-object traceback** (Incident Responder's JTBD, Architect's "which PRs implement Requirement X" query) — this genuinely could be 10x versus reconstructing the same answer by hand across GitHub Issues search + PR search + grep; (2) **agent actions that are structurally equal, audited, and approvable exactly like human actions in one unified review surface** (the Reviewer/Manager JTBDs — "show me the evidence... in one place, not scattered across five tools") — this is plausibly 10x versus today's fragmented world of separate AI-tool dashboards, GitHub PR reviews, and a separate audit log; (3) **a single AI Gateway that lets an org swap/mix model providers without touching application code or agent configuration** — genuinely valuable for cost/vendor-risk management, though more like 2-3x than 10x for an individual developer's daily experience.

Now testing against the actual post-Phase-9 MVP scope (master doc §48, Phase 9 §3): (1) is **present** at MVP (GRF-REQ-008 query API, exercised by Phase 9 DoD step 9) — genuinely kept. (2) is **partially present**: AGT-REQ's full P0 set and UX-REQ-003 are MVP, so the *mechanism* exists — but "one unified review surface... not scattered across five tools" is precisely UX-REQ-002 (context-assembled pages), which is **V1, not MVP** (master doc §48). The mechanism (data model, approval gate) ships at MVP; the *experience* that would make it feel 10x rather than merely "technically auditable" does not. (3) is **not meaningfully present** at MVP: AI-REQ-005 (swap providers without app changes) is V1, and per RT-02 above, MVP ships with effectively one hardcoded provider.

**This is the sharpest finding in the whole document, worth stating plainly: of the three most plausible 10x differentiators derivable from this program's own stated value proposition, exactly one (cross-object traceback) ships with its full experiential impact at MVP. The other two ship their backend mechanism at MVP but defer the actual user-facing 10x moment (unified review surface; provider-agnostic Gateway) to V1** — meaning Phase 9's rigorous, well-justified, load-bearing-test-driven cuts, applied consistently and defensibly requirement-by-requirement, nonetheless had the *emergent, cross-cutting* effect of leaving MVP with genuine plumbing but only one-of-three of the moments that would make a real user say "I couldn't have gotten this anywhere else." Phase 9 never ran this specific check (it tested requirement-by-requirement load-bearing-ness for loop *completion*, never asked "which 3 things would make a user *switch*, and are they still here") — this is a distinct question from the loop-completion test, and the two questions produce different, non-overlapping cut sets.

**Attacks:** Phase 9's entire MVP Cut List methodology (§1/§2) — not any single cut, but the *absence of a "genuine 10x" cross-check* as a category of test alongside "is it load-bearing for the loop."

**Mitigation:** `[PROPOSAL]` This is one of the three most dangerous findings (see rollup below). Recommend Phase 13 explicitly re-examine whether UX-REQ-002 (or a minimal slice of it — not the full "progressive disclosure" apparatus, just "PR/Review page shows linked Requirement/CI/Policy state inline") should be pulled forward to MVP specifically *because* it's one of the few things standing between "the graph exists and is queryable" and "a Reviewer actually experiences a 10x moment" — this is the same fix proposed independently in RT-01 (Angle 1) from a different angle, which strengthens rather than weakens the case: two independent adversarial attacks on this document converged on the same requirement (UX-REQ-002) as the one Phase 9 correctly identified as non-load-bearing for loop *completion* but this pass identifies as load-bearing for loop *worth having built*.

## The 3 Most Dangerous Findings

These three require an explicit response before Phase 13's final baseline — they should not get buried in the list above.

### 1. RT-10 — Platform-process compromise is an uncovered threat model (Critical)
Phase 10's monolith-first architecture (correctly justified against microservice over-engineering) concentrates Policy evaluation, credential issuance, sandbox spawning, and audit-log writes in one process. No AISEC-REQ item, and no line in the Risk Register (master doc §53), treats "the Platform process itself is compromised" as a distinct scenario from "an agent misbehaves within its granted scope" — yet a compromised Platform process can rewrite the very audit trail (GRF-REQ-003/SEC-REQ-003) meant to make agent-inclusive accountability trustworthy, undermining Principle 7 (Evidence-Native) and Principle 5 (Agent-Native) simultaneously at their structural root. This is the single largest gap between "the requirements say agents are audited like humans" and "the architecture actually guarantees that under a realistic threat model."

### 2. RT-17 — The MVP may ship plumbing without the 10x moment (Critical)
Phase 9's rigorous, defensible, requirement-by-requirement cuts optimized for "does the loop complete" and never separately tested "does this still contain what would make someone switch." The result: of three plausible 10x differentiators derived from this program's own stated value proposition, only one (cross-object traceback) survives to MVP with its full user-facing impact; the other two (unified review experience, provider-agnostic AI) ship backend mechanism only, with their experiential payoff deferred to V1. A technically-complete MVP that doesn't make anyone say "I couldn't get this anywhere else" is a real risk to the whole program's premise, independent of whether any individual cut was well-reasoned in isolation.

### 3. RT-14 — MVP ships with zero AI cost visibility for a persona that pays the bill directly (Critical)
Self-hosted MVP adopters run AI Gateway calls and full agentic coding sessions against their own metered API accounts with no requirement-guaranteed cost/token visibility until V1 (AI-REQ-002 demoted). This is inconsistent with Phase 9's own successful reasoning for keeping AGT-REQ-006 (resource limits) at MVP for the identical risk class ("can trivially run away on cost/time"), and it makes the MVP less transparent on this dimension than the very AI coding tools it competes with. This is a near-term financial and trust risk for the platform's earliest, most committed adopters — precisely the audience whose goodwill the program can least afford to spend.
