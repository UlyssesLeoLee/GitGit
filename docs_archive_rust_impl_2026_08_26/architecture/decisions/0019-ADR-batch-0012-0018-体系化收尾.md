# ADR-0019: ADR 编号体系化收尾 (0012-0019 批次)

> **Status**: Proposed
> **Date**: 2026-08-23
> **Deciders**: SA + TL + EM
> **Consulted**: —
> **Informed**: 全部

## Context and Problem Statement

[技术选型 §18 后续 ADR](../tech-selection.md#18-后续-adr-引用-future-adrs) 列出了 8 个待写 ADR,使用了 `ADR-002` ~ `ADR-008` 的编号,但**与现有 `docs/architecture/decisions/0001-0009-*.md` 编号冲突**。

冲突具体表现:
- 现有 `0002-*.md` 主题是"Git 读路径 gix/写路径 shell git"
- [技术选型 §18](../tech-selection.md#18-后续-adr-引用-future-adrs) 的 `ADR-002` 主题是"gix 读路径**具体模块边界**"
- 两个文件都是关于 gix,但**粒度不同**: 0002 是技术选型决策;0010 是模块边界划分

本 ADR 收尾本次批次(0012-0018),并明确:
1. 未来 ADR 编号统一为 `0018+`
2. 0012-0018 与 0001-0009 之间的关系(细化 vs 重写)
3. 仍待决议的 ADR 清单

## Decision Drivers

- [DRIVER-1] 文档可追溯性: cross-doc 引用必须能精确定位
- [DRIVER-2] 编号不重叠,避免歧义
- [DRIVER-3] 0012-0018 与 0001-0009 是"细化 / 落地"关系,不是"重写 / 替代"
- [DRIVER-4] 维护成本低

## Considered Options

1. **Option A — 0012+ 续号;旧编号 0001-0009 保留** (本次推荐)
2. **Option B — 全部重新编号(0001 全新,旧 0001-0009 标记为 Legacy)**
3. **Option C — 用 `0001-a` `0001-b` 子编号**

## Decision Outcome

**Chosen option**: "Option A — 0012+ 续号;旧编号 0001-0009 保留", because 改动最小;旧的 9 个 ADR 仍可读;新 ADR 在链接上明确指明 `0012-0018` 即可。

## Pros and Cons of the Options

### Option A — 0012+ 续号
[+] 改动最小;旧 ADR 不动
[-] 编号视觉上不连续(0001-0011 然后 0012+)

### Option B — 全部重新编号
[+] 编号连续
[-] 旧 ADR 全部 supersede;git blame 失忆;返工成本高

### Option C — 子编号
[+] 视觉关联
[-] 编号不扁平;cross-doc 引用容易写错
